This page is the normative specification for **Reconify Engine Agent Protocol v1**. It defines the
commands, schema identifiers, error shape, exit codes, inference gates, and flag-precedence rules that
external agents (Claude Code, Codex, Gemini CLI, OpenCode, or any scripted caller) can rely
on across releases.

The keywords **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are used as defined in RFC 2119.

This document describes the target contract for the roadmap tracked in the `agent-protocol` label. Each
implemented command and schema MUST match this spec.
[`reference/cli`](/docs/cli/reference/cli) and
[`reference/result-schema`](/docs/cli/reference/result-schema) remain the source of truth for what is
already implemented.

## Naming

- The OSS executable name **MUST** remain `reconify`. This protocol does not rename the binary, the Go
  module, the repository, `reconify.yaml`, or the `RECONIFY_CONFIG` environment variable.
- Agent-facing schemas, skills, and capabilities **MUST** identify the interface as
  **Reconify Engine**.
- Versioned schema identifiers **MUST** use the `reconify.engine.*` namespace (see
  [Schema identifiers](#schema-identifiers)).
- A future hosted/platform CLI may use the name `reconify-cloud`. It is out of scope for
  this repository and this protocol.
- This protocol MUST NOT reorganize the documentation hierarchy in `docs/content/docs/`.

## Scope: Engine vs. Cloud

Reconify Engine is the deterministic, local, file-oriented interface specified here: the `reconify`
binary and its output formats. It establishes
deterministic financial facts from local files and requires no account, authentication, or network
access.

A distinct, not-yet-built **Reconify Cloud** interface may later add hosted accounts, authentication,
issue tracking, eventing, integrations, and monitoring. Reconify Cloud is explicitly out of scope for
this protocol and for every issue in the `agent-protocol` roadmap. Nothing in this spec MAY be
interpreted as a commitment about Cloud's naming, transport, or schemas.

## Target workflow

Agents are expected to drive Reconify through this sequence:

```
capabilities → inspect → infer config → validate → reconcile → explain
```

- `capabilities` — self-describe the installed Engine's protocol version, commands, formats, and schemas.
- `inspect` — profile an input file deterministically before writing a config.
- infer config — propose a `reconify.yaml` from two sample files.
- validate — confirm the config or proposal is well-formed (`reconify config validate` /
  `check-source`, both already implemented).
- reconcile — run the deterministic match.
- explain — summarize a completed result without re-running reconciliation.

An agent MAY skip steps it already has enough information for (for example, calling `reconcile` directly
with a hand-written config), but MUST NOT assume a step's output shape without first calling
`capabilities` or reading this page.

## Capabilities

`reconify capabilities` prints a JSON document to stdout using the
`reconify.engine.capabilities.v1` schema. It is the preferred first call for an agent that needs to
discover the installed Engine surface. The document includes the Engine version, supported commands,
input/output formats, matching passes, result modes, published schema identifiers, diagnostic codes,
and process exit codes.

The published Draft 2020-12 schema is
[`schemas/reconify.engine.capabilities.v1.json`](https://github.com/reconifyhq/reconify/blob/main/schemas/reconify.engine.capabilities.v1.json).
Installed binaries expose the same document with `reconify schema capabilities`.

```json
{
  "schema": "reconify.engine.capabilities.v1",
  "protocol_version": "v1",
  "protocol_versions": ["v1"],
  "engine": {"name": "Reconify Engine", "version": "0.4.0"},
  "commands": {"reconcile": {"description": "...", "interactive": false}},
  "formats": {"reconcile": {"formats": ["json", "json-stream", "ndjson", "csv", "table"], "default": "json"}},
  "matching": {"passes": [], "default_passes": ["reference_one_to_one"], "group_keys": ["reference", "name", "group_key"]},
  "result_modes": ["all", "exceptions_only", "summary_only"],
  "schemas": {"result": "reconify.engine.result.v1", "diagnostic": "reconify.engine.diagnostic.v1"},
  "error_codes": {},
  "exit_codes": {"0": "Success."}
}
```

## Inspect

`reconify inspect FILE` prints a JSON document to stdout using the `reconify.engine.profile.v1`
schema. It deterministically profiles a CSV, JSON, NDJSON, XLSX, or XLSM file's format, per-column
type inference, date layouts, and amount formats **before** a `reconify.yaml` mapping exists. It does
not propose a column mapping or config; `config infer` (AP-6) builds on this profile to do that.

By default `inspect` scans up to 1,000 rows; `--full` performs an exact scan of every row instead. Up
to three representative, distinct raw values per column are included by default, configurable with
`--sample-values` (`0` disables sample collection entirely).

```json
{
  "schema": "reconify.engine.profile.v1",
  "file": "payments.csv",
  "format": "csv",
  "scan": {"full": false, "rows_scanned": 1000, "truncated": true},
  "columns": [
    {
      "name": "date",
      "non_empty_count": 1000,
      "null_count": 0,
      "inferred_type": "date",
      "ambiguous": false,
      "candidates": [{"type": "date", "confidence": 0.99}, {"type": "text", "confidence": 0.01}],
      "date_layout": "2006-01-02",
      "sample_values": ["2024-01-01", "2024-01-02", "2024-01-03"]
    }
  ]
}
```

Each column reports every type hypothesis considered (`date`, `amount`, `integer`, `boolean`, `text`,
or `empty` for an all-empty column) ranked by confidence (the fraction of non-empty sampled values that
matched). `ambiguous` is `true` when the top two candidates are within a 0.10 confidence lead of each
other — a fact about the column, not a decision; `inspect` never gates or proposes a mapping.

The published Draft 2020-12 schema is
[`schemas/reconify.engine.profile.v1.json`](https://github.com/reconifyhq/reconify/blob/main/schemas/reconify.engine.profile.v1.json).
Installed binaries expose the same document with `reconify schema profile`.

## Schema identifiers

Every schema identifier under this protocol follows `reconify.engine.<name>.v1`. The `v1` suffix is a
whole-document version: a breaking change to any field of a payload requires `v2` for that identifier
specifically; identifiers version independently of one another.

| Identifier | Emitted by | Status |
|---|---|---|
| `reconify.engine.result.v1` | `reconcile` (JSON / json-stream top level, and every NDJSON envelope) | Published — AP-2 |
| `reconify.engine.diagnostic.v1` | any command, on error, when `--error-format json` or `--agent` | Published — AP-3 |
| `reconify.engine.capabilities.v1` | `capabilities` | Published — AP-4 |
| `reconify.engine.profile.v1` | `inspect` | Published — AP-5 |
| `reconify.engine.config-proposal.v1` | `config infer` | Published — AP-6 |
| `reconify.engine.explanation.v1` | `explain` | Published — AP-8 |

Rules that apply to every identifier:

- Adding this identifier to an existing payload (for example, a `schema` field on the top-level
  `reconcile` JSON result) MUST NOT rename or remove any field or NDJSON event name that already exists.
  See [`reference/result-schema`](/docs/cli/reference/result-schema) for the current, canonical field
  list that this constraint protects.
- New fields added under a `vN` identifier MUST be additive and MUST be safe to ignore by a consumer that
  only understands the fields documented at the time it was written.
- A schema identifier MUST NOT be reused for an incompatible shape. A breaking change creates
  `reconify.engine.<name>.v2` while `v1` continues to be emitted for at least one deprecation window
  documented in the changelog.

## Commands in scope

This protocol covers the following command surface. Commands marked "existing" are already implemented
and are only constrained here with respect to the additive schema/diagnostic changes above; see
`reference/cli` for their full flag reference.

| Command | Status | Spec issue |
|---|---|---|
| `reconify reconcile` | implemented, gains `reconify.engine.result.v1` and `--agent` | AP-2, AP-7 |
| `reconify parse` | existing, unaffected by this protocol | — |
| `reconify config validate` | existing, unaffected | — |
| `reconify config check-source` | existing, validates a bounded row sample by default | #90 |
| `reconify config init` | existing, unaffected | — |
| `reconify config schema` | existing, remains operational; `capabilities` supersedes it as the agent entry point but does not replace it | AP-4 |
| `reconify capabilities` | implemented | AP-4 |
| `reconify inspect FILE` | implemented | AP-5 |
| `reconify config infer` | implemented | AP-6 |
| `reconify explain` | implemented | AP-8 |
| `reconify reconcile --auto` | implemented | AP-12 |
| `--agent` (global flag) | implemented | AP-7 |

`reconify doctor` is explicitly deferred: capability discovery (`capabilities`), config validation, and
source checking (`config check-source`) already cover the readiness checks a `doctor` command would
provide. No issue in this roadmap adds it.

## Diagnostic model

Reconify emits the versioned diagnostic envelope on stderr when `--error-format json` is set. The
legacy fields remain available for callers that only understand the original contract:

```json
{"error": "<message>", "code": "<err-code>"}
```

Both fields **remain present, unrenamed, and unchanged in meaning** indefinitely. The versioned schema
adds a nested, richer diagnostic alongside them, not instead of them:

```json
{
  "error": "<message>",
  "code": "<err-code>",
  "ok": false,
  "schema": "reconify.engine.diagnostic.v1",
  "diagnostic": {
    "code": "<granular machine-readable code>",
    "category": "<config | input | inference | execution | internal>",
    "message": "<human-readable message>",
    "details": { "...": "..." },
    "suggestions": ["<actionable next step>"]
  }
}
```

- `ok` MUST be `false` on every error envelope and `true` on every successful structured response that
  adopts this diagnostic shape.
- `diagnostic.code` MAY be more granular than the legacy `code` field (for example, distinguishing
  `INFERENCE_AMBIGUOUS` from a generic `config_error`), but the legacy `code` MUST still be one of the
  existing values documented in `reference/cli`.
- A command MUST NOT introduce a diagnostic-only failure mode that has no corresponding legacy `error`/
  `code` pair, so that scripts written against the legacy contract keep working unmodified.

## Exit codes

The exit codes already documented in `reference/cli` and `reconify config schema` are canonical and
MUST NOT change meaning:

| Code | Meaning |
|---|---|
| `0` | Success. |
| `1` | Unexpected or internal error. |
| `2` | Config or validation error. |
| `3` | Reconcile completed with unmatched rows (`--fail-if-unmatched` only). |
| `4` | Reconcile completed with exception events (`--fail-if-exceptions`; takes precedence over `3`). |

New commands introduced by this protocol MUST reuse this table rather than inventing new numeric codes,
with these clarified applications:

- `config infer` returns exit code `0` when it successfully produces a proposal, even when that
  proposal's `status` is `needs_input` rather than `ready` — producing a needs-input proposal is not a
  failure.
- `config infer --out <file>.yaml` that cannot resolve ambiguity to a single confident mapping MUST NOT
  write the output file and MUST return exit code `2`, with diagnostic code `INFERENCE_AMBIGUOUS`.
- `reconcile --auto` that fails its confidence gate (see below) MUST emit `INFERENCE_AMBIGUOUS` to stderr,
  MUST NOT emit any result data, and MUST return exit code `2`.
- Command-line usage errors (unknown command or flag, wrong argument count, invalid flag value) return
  exit code `2` with diagnostic code `USAGE_ERROR` (category `usage`) and legacy code `config_error`.
  `details.usage` carries the usage line and `details.did_you_mean` the closest valid command or flag.
- `verify` returns exit code `0` when every check passes or is skipped. Any failing check returns exit
  code `2` with legacy code `config_error`: `CONFIG_INVALID` when the config is invalid, otherwise
  `VERIFICATION_FAILED` (category `verification`). The checklist is still written to stdout.

## Config inference gates

Any command that infers a `reconify.yaml` mapping (`config infer`, and `reconcile --auto` internally)
MUST apply the same gate before returning `status: ready` or proceeding to reconcile:

- Date, amount, and reference mappings each MUST reach confidence **>= 0.90**.
- Each of those mappings MUST have a **>= 0.10** confidence lead over its next-best candidate column.
- Confidence MUST be computed from **at least 100 successfully parsed sample rows** per source. Fewer
  successfully parsed rows MUST NOT produce a `ready` status.

When any of these gates fails, the command MUST return `status: needs_input` (for `config infer`) or the
`INFERENCE_AMBIGUOUS` diagnostic (for `reconcile --auto`) rather than guessing.

Inferred defaults, when a proposal is produced, MUST be:

- One-to-one reference matching (no `passes` override, no `name_mode: tokens`).
- A `1d` date window.
- Zero amount tolerance.
- No name matching.

An agent MAY override any inferred default by editing the proposed config before running `reconcile`;
`reconcile --auto` MUST use exactly the inferred defaults and MUST NOT accept a `--pair`, `--config`, or
file-list override in the same invocation (see [Auto reconciliation](#auto-reconciliation)).

## Flag precedence

Reconify's existing precedence pattern, demonstrated today by `--result-mode` vs. per-pair
`result_mode`, and by `--config` vs. `RECONIFY_CONFIG`, is:

**explicit CLI flag > per-pair/config value > built-in default.**

This protocol's new flags MUST follow the same pattern:

- `--agent` sets defaults for output format, error format, and result mode. Any flag the caller sets
  explicitly (`--format`, `--error-format`, `--result-mode`, etc.) MUST override the `--agent` default.
  `--agent` MUST NOT imply `--fail-if-exceptions` or `--fail-if-unmatched` — those remain opt-in.
- `--agent` MUST reject commands that require interactive input (for example, `config init`, which today
  has no non-interactive mode — `--force` only bypasses the destination-file overwrite check in
  `ensureCanWriteConfigInit`, not the `huh` wizard in `runConfigInit`) with a structured diagnostic that
  names a non-interactive alternative (such as `config infer`, once implemented, or hand-writing
  `reconify.yaml`), instead of blocking on a prompt.
- Config inference defaults (above) apply only when the corresponding field is not already pinned by an
  explicit flag or an existing config value being extended.

## Auto reconciliation

`reconify reconcile LEFT RIGHT --auto` (AP-12):

- MUST accept exactly two positional file arguments.
- MUST be mutually exclusive with an explicitly supplied `--config`, `--pair`, or any other file/source
  override; supplying both is a config error (exit code `2`).
- MUST run inference (the same gate as `config infer`) before reconciling, and MUST NOT reconcile when
  the gate fails.
- MUST emit reproducibility metadata containing the exact inferred config and its confidence alongside
  the result, so the run can be reproduced non-auto by writing that config to a file.

## Evaluation and skills surface

Two roadmap issues extend this protocol without changing its schemas:

- The evaluation corpus and cross-agent runner (AP-9, AP-10) exercise this protocol end-to-end against
  external coding agents; they MUST treat this page, not agent-specific prompting, as ground truth for
  expected behavior.
- Canonical skills MUST be published under the `reconify-engine-*` namespace (AP-11); existing
  `reconify-*` skill names remain as deprecated thin adapters and MUST continue to work.

## Compatibility rules

- Every change under this protocol is additive. Nothing on this page authorizes renaming or removing an
  existing CLI flag, config key, output field, or NDJSON event name.
- Existing reconciliation event names (`match`, `amount_diff`, `timing_diff`, `unmatched_left`,
  `unmatched_right`, `grouped_match`, `grouped_amount_diff`, `grouped_timing_diff`,
  `many_to_many_match`, `many_to_many_amount_diff`, `many_to_many_timing_diff`, `ambiguous_group`,
  `duplicate`, `source_summary`, `summary`, `run_info`) are canonical. This protocol MUST NOT introduce a
  replacement exception taxonomy.
- `reconify config schema` remains operational and MUST stay in sync with this page; `capabilities`
  (AP-4) is additive to it, not a replacement.
